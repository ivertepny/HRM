# Доступ: ролі, дозволи, області

Документ для HR і адміністраторів системи: хто що бачить і як це налаштувати.
Усе описане налаштовується в розділі **Адміністрування → Ролі та доступ**.

## Коротко

- **Дозвіл** — одна дія над одним ресурсом, наприклад `vacations:manage`
  («схвалювати відпустки»).
- **Роль** — набір дозволів з назвою, наприклад «HR Manager». Ролі можна
  створювати свої.
- **Призначення** — роль, видана конкретній людині:
  - **на всю компанію** або **лише на підрозділ** (разом з усіма вкладеними
    підрозділами);
  - **безстроково** або **до певної дати**.
- **Власні дані** людина бачить завжди, без жодних дозволів: свій профіль,
  зарплату, кадрову історію, документи, обладнання, відпустки й табель.

Одна людина може мати кілька призначень, тоді її права складаються.
Наприклад, роль «Employee» на всю компанію плюс «Team Lead» лише на відділ
Backend.

## Дозволи

| Ресурс | Дія | Що дає |
|--------|-----|--------|
| `users` | `read` | бачити облікові записи |
| | `write` | створювати й редагувати облікові записи, надсилати запрошення |
| | `delete` | видаляти облікові записи |
| `employees` | `read` | бачити профілі працівників |
| | `write` | прийом, переведення, зміна профілю, звільнення |
| | `delete` | видаляти профілі |
| `salary` | `read` | бачити чужі зарплати |
| | `write` | змінювати зарплати |
| `documents` | `read` | бачити й завантажувати чужі документи (CV, NDA, договори) |
| | `write` | додавати документи |
| | `delete` | видаляти документи |
| `company` | `read` | бачити оргструктуру |
| | `write` | створювати й редагувати підрозділи |
| | `delete` | закривати підрозділи |
| `roles` | `read` | бачити ролі і хто їх має |
| | `manage` | створювати ролі і видавати їх |
| `vacations` | `read` | бачити чужі відпустки |
| | `write` | подавати заявки на відпустку |
| | `manage` | схвалювати, відхиляти й скасовувати чужі заявки, подавати за інших |
| `equipment` | `read` | бачити обладнання (і склад) |
| | `manage` | облік, видача, повернення, списання |
| `attendance` | `read` | бачити чужий табель і місячний звіт |
| | `write` | відмічати власну присутність |
| | `manage` | вести календар святкових (неробочих) днів; лише на всю компанію |
| `ai` | `use` | користуватися AI-асистентом |

**Шаблони замість переліку:**
- `employees:*` — усі дії над ресурсом;
- `*:*` — узагалі всі дозволи.

Шаблон покриває й ті дії, які з'являться пізніше.

## Системні ролі

Створюються автоматично. Їх не можна видалити чи перейменувати, а склад
відновлюється командою `seed_roles --reset-system-roles`.

| Роль | Склад | Для кого |
|------|-------|----------|
| **Employee** | `employees:read`, `company:read`, `vacations:write`, `attendance:write`, `ai:use` | кожен працівник; видається автоматично при створенні облікового запису |
| **HR Manager** | `employees:*`, `salary:*`, `documents:*`, `users:read`, `company:read`, `vacations:*`, `equipment:*`, `attendance:read`, `attendance:manage`, `ai:use` | кадровики |
| **System Admin** | `*:*` | адміністратори системи |

Чому в Employee немає `salary:read`: свою зарплату працівник і так бачить, а
`salary:read` відкрив би йому чужі.

## Області (scope)

Призначення **без підрозділу** діє на всю компанію. Призначення **з
підрозділом** діє лише на людей і дані цього підрозділу та всіх вкладених.

Приклад. Петру видали роль з `vacations:manage` і `attendance:read` на
підрозділ **IT**. Тоді він:
- схвалює відпустки й бачить табель працівників IT, Backend і Frontend;
- заявок відділу HR не бачить узагалі: їх немає ні у списках, ні у звіті, а
  пряме посилання дає «не знайдено».

Так налаштовується керівник команди. Він має роль з потрібними дозволами,
видану на його підрозділ, і бачить лише своїх людей.

Область перевіряється в кожному розділі:
- списки, звіти й пошук показують лише дані з області;
- дії над людиною (переведення, зарплата, документ, видача обладнання)
  перевіряються в її підрозділі. Переведення — і в старому, і в новому
  підрозділі.

## Тимчасові ролі

У призначення можна вказати дату закінчення. Наприклад, заступник керівника
на час відпустки отримує `vacations:manage` на відділ до кінця місяця. Після
цієї дати роль просто перестає діяти; видаляти її вручну не потрібно.

## Обмеження, які діють завжди

- **Не можна видати більше, ніж маєте самі.** Створити роль, видати її чи
  відкликати можна, лише якщо у вас самих є всі її дозволи в цьому підрозділі.
  HR з областю «IT» не видасть комусь роль на всю компанію чи на HR.
- **Свою заявку на відпустку не розглядають.** Навіть HR чи адміністратор не
  може схвалити власну відпустку: її розглядає хтось інший.
- **Табель відмічають лише за себе.** `attendance:read` дає бачити чужий
  табель і звіт, але не правити його. Виправити свою відмітку можна протягом
  7 днів (налаштування `ATTENDANCE_EDIT_DAYS`).
- **Зарплата прихована і від тих, хто бачить профіль.** Без `salary:read` у
  підрозділі людини поле зарплати в її профілі порожнє.
- **Документи й фото видно лише тим, хто бачить їхнього власника.** Пряме
  посилання на файл не допоможе: доступ перевіряється при кожному
  завантаженні.
- **AI-асистент знає стільки, скільки ви.** Про оргструктуру він відповідає
  лише в межах вашого `company:read`.
- **Вимкнений обліковий запис не має жодних прав**, незалежно від ролей.

## Як налаштувати типові ситуації

| Ситуація | Що зробити |
|----------|------------|
| Новий працівник | Адміністрування → Облікові записи: створити запис — людина отримає на пошту запрошення і сама задасть пароль (посилання діє 7 днів; «Надіслати запрошення ще раз» — на сторінці запису). Потім там само — «прийом на роботу» (підрозділ, посада). Роль Employee видається сама. |
| Новий кадровик | Видати **HR Manager** на всю компанію або на свою філію. |
| Керівник команди | Створити роль, наприклад «Team Lead»: `vacations:read`, `vacations:manage`, `attendance:read`, `employees:read`. Видати її на підрозділ команди. |
| Керівник бачить зарплати команди | Додати до його ролі `salary:read` (призначення вже обмежене підрозділом). |
| Заміна на час відпустки | Видати ту саму роль на той самий підрозділ з датою закінчення. |
| Завгосп | Роль з `equipment:read` і `equipment:manage` на всю компанію. |
| Людина звільнилась | Звільнення в профілі (дата звільнення). Потім перевести обліковий запис у статус «неактивний»: вхід закриється, усі права зникнуть. |

## Паролі

- **HR чи адміністратор паролів не знає і не задає.**
  - Новий запис отримує на пошту запрошення, і пароль людина ставить сама.
  - Поки цього не сталося, увійти неможливо, а на сторінці запису видно
    «Запрошення не прийнято».
- **Забутий пароль людина скидає сама:** «Забули пароль?» на сторінці входу.
  Посилання з листа діє 2 години і лише один раз.
- **Після зміни пароля** всі сесії людини на інших пристроях завершуються.
- **Вимкнений обліковий запис** не отримає ні запрошення, ні листа зі
  скиданням.

## Для адміністраторів системи

- **Каталог дозволів** — у коді, `apps/access/catalog.py`. Нові дозволи
  з'являються в базі після `python manage.py seed_roles`. Склад системних
  ролей оновлюється з `--reset-system-roles`, а дозволи, яких уже немає в
  каталозі, прибирає `--prune`.
- **Суперкористувач Django** (`is_superuser`) має всі права, як із `*:*`.
  Створюється лише з сервера командою `createsuperuser`; в інтерфейсі такої
  можливості немає.
- **Зміни ролей діють одразу.** Права кешуються (до 5 хвилин), але будь-яка
  зміна ролей чи призначень скидає кеш. Тимчасова роль перестає діяти рівно в
  момент закінчення.
- **Хто кому що видав** — у списку призначень: там є автор і дата видачі.
